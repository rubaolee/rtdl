**File:** `src/native/optix/rtdl_optix_workloads.cpp:7395`

`lp.probe_count` and `lp.point_index_offset` change per chunk, so `upload(prepared_points->d_params.ptr, &lp, 1)` still runs on every loop iteration. **Yes.**

The struct definition at `rtdl_optix_workloads.cpp:6366–6400` contains only:
- `point_count` (size_t)
- `points_x`, `points_y`, `point_ids` (host-side vectors)
- `d_points_x`, `d_points_y`, `d_point_ids`, `d_count`, `d_params` (DevPtr device buffers)

No RayJoin-specific fields or naming appear in the struct or its constructor. The count function body at lines 7309–7417 has no reference to RayJoin. The test's `assertNotIn("rayjoin", count_body.lower())` check over the count function body validates this structurally.

The two new struct members (`d_count`, `d_params`) are allocator-agnostic: `DevPtr(sizeof(uint32_t))` and `DevPtr(sizeof(PipLaunchParams))`. `PipLaunchParams` is the generic OptiX PIP launch params struct, not a RayJoin-specific type. The `goal` field in the artifact is `3244` (the benchmark runner schema), which is correct; it does not indicate RayJoin-specific native logic.

### Q2: Does the implementation really reuse `PreparedPointProbeColumns2D::d_count` and `PreparedPointProbeColumns2D::d_params` instead of allocating per count call?

**Yes.**

Constructor (`rtdl_optix_workloads.cpp:6385–6386`):
```cpp

d_params(sizeof(PipLaunchParams))
```
Both buffers are allocated once at construction time.

Count function (`rtdl_optix_workloads.cpp:7344, 7383, 7395, 7410`):
- `upload<uint32_t>(prepared_points->d_count.ptr, &zero, 1)` — resets existing buffer
- `upload(prepared_points->d_params.ptr, &lp, 1)` — uploads to existing buffer

No local `DevPtr d_count(sizeof(uint32_t));` or `DevPtr d_params(sizeof(PipLaunchParams));` appear in the count function body. The test's two `assertNotIn` checks verify this absence.

### Q6: Is the recommended next direction sound — batched/replayed scalar-count launches or a more compact generic closed-shape predicate-count path, rather than another tiny allocation tweak?

**Yes.**

The bottleneck is clearly the synchronous per-chunk launch cycle at line 7405 (`cuStreamSynchronize`), which accounts for ~0.262 ms of the 0.303 ms total. The per-iteration cost is now:
1. `upload` zero (4 bytes HtD)
2. `upload` lp struct (PipLaunchParams HtD)
3. `optixLaunch` + `cuStreamSynchronize`
4. `download` count (4 bytes DtH)

With allocation overhead eliminated, the dominant cost is the synchronous barrier. Batching multiple scalar-count queries into a single asynchronous stream before synchronizing once — or fusing the count kernel to avoid the upload/download round-trip entirely — would be the natural next step, and is what the report and `future_version_to_do_list.md` both recommend.

The `future_version_to_do_list.md` entry at line 26–28 (added by Goal3308) correctly summarizes the lesson: workspace allocation was not the bottleneck; the synchronous launch/download cycle dominates. A further single-allocation tweak is unlikely to move the needle meaningfully.

The constraint "should not relax inclusive boundary semantics or reintroduce app-specific native logic" is appropriate and correctly carried forward from Goal3306's approved direction.

## Summary

Goal3308 is a clean, well-bounded allocation-reuse change. `d_count` and `d_params` are correctly moved into the struct constructor and reused per count call; the count function no longer allocates per call. The native change is app-agnostic. The artifact fully supports the reported 0.317 → 0.303 ms improvement on the RTX A5000 pod at commit `8d8e7c02`. Count 1430 is consistent across all 20 repeats; inclusive-boundary validation ran outside the timed lane on every repeat; all claim-boundary flags are false; and next-direction guidance is sound. No correctness issues found.
