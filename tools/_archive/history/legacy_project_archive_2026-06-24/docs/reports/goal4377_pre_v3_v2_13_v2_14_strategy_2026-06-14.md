# Goal4377 Pre-V3 Strategy: v2.13 Internal Bridge, v2.14 Cleanup Release, and the V3.0 Target

Date: 2026-06-14

Status: planning / decision record for external review.

This document records the post-RayJoin discussion that followed the Goal4376
overlay point-location optimization. It does not authorize a release, a tag
move, broad RT-core speedup wording, whole-application speedup wording,
RTDL-beats-RayJoin wording, RayJoin paper reproduction wording, automatic
partner selection, Intel/AMD GPU wording, or true zero-copy/device-residency
wording.

## 1. Context

The RayJoin work forced a sharper separation between three claims:

1. RTDL can express and run serious benchmark-app workloads using Python,
   partners, and app-agnostic native RTDL primitives.
2. RTDL OptiX/RT-core routes can beat same-RTDL Embree CPU routes on selected
   scoped rows when the contract and partner choices are fixed.
3. RTDL's generic path can match the hot-processing efficiency of an expert
   hand-written C++/CUDA/OptiX implementation.

The first two claims have useful evidence. The third is not yet proven.

The immediate trigger was RayJoin Section 5.7 polygon overlay, especially the
Block x Water row. After Goal4376, the available rows look like this:

| Row | Author RT process wall | Old RTDL OptiX | Goal4376 RTDL OptiX | RTDL Embree CPU | Immediate interpretation |
| --- | ---: | ---: | ---: | ---: | --- |
| County x Zipcode | 5.614s | 5.819s | 5.767s | 9.954s | RTDL OptiX is near author process wall and faster than Embree under the RTDL route. |
| Block x Water | 28.088s | 42.380s | 28.471s | 34.905s | The previous Embree-faster result is fixed; RTDL OptiX is near author process wall and faster than Embree under the RTDL route. |

However, the author RT process wall time and RTDL OptiX wall time are not the
same kind of hot-compute evidence. The Block x Water author run spends most of
its process wall in reading/deserializing maps. Its printed processing phases
include approximately:

| Author phase | Printed time |
| --- | ---: |
| Intersection edges | 24.6 ms |
| Map 0 locate vertices | 92.0 ms |
| Map 1 locate vertices | 54.6 ms |
| Compute output polygons | 84.2 ms |

By contrast, RTDL's Goal4376 Block x Water run records about 8.58s of exposed
OptiX traversal/launch time and 28.47s total application/runtime wall time. That
means the public comparison can responsibly say "near author process wall under
the cached/preprocessed application-wall protocol"; it must not say "RTDL hot
compute matches the author C++/CUDA/OptiX implementation."

## 2. Design Conclusion

The next high-value target is not merely "use RT cores." Both RayJoin and RTDL
already use OptiX and therefore use NVIDIA RT hardware for traversal. The next
target is:

> Preserve app-agnostic RTDL semantics, but lower RayJoin-style and other
> benchmark-app workloads into fused, device-resident primitive graphs whose
> ray-workload shape approaches expert C++/CUDA/OptiX implementations.

This is a V3.0-class goal. It is larger than v2.13/v2.14 cleanup because it
requires RTDL to evolve from a primitive library into a primitive planner and
execution-graph system.

## 3. What Current RTDL Can and Cannot Do

Current RTDL can already support the right architecture:

- Native engine primitives can remain app-agnostic.
- App logic can stay in Python and partner code.
- Native OptiX/Embree surfaces can expose generic prepared handles, compact
  outputs, face-id/device-column outputs, and route-specific timing.
- Partners such as CuPy or Numba can own ordinary GPU or CPU continuation work
  when a fused RTDL primitive is not the right contract.

Current RTDL does not yet automatically produce author-level hot paths:

- LSI, PIP, midpoint classification, topology work, and output assembly still
  cross several primitive/app boundaries.
- Intermediate row streams can still be dumped, reconstructed, or materialized
  in ways a specialized author implementation avoids.
- Device-resident stream contracts are partial, not yet the default app graph.
- The runtime lacks a planner that chooses RT traversal, CUDA partner kernels,
  compact streams, summaries, and reductions as one optimized graph.
- Current phase accounting is strong enough for app-wall and exposed traversal
  statements, but not yet a full CUDA-event/Nsight breakdown for every kernel,
  copy, build, and RT traversal phase.

## 4. Versioning Decision Proposed for Review

The repository already contains a v2.13 source-tree release package and a
`VERSION` marker set to `v2.13`. Therefore this document must not silently
rewrite history.

The proposed governance sequence is:

| Version step | Role | Release posture |
| --- | --- | --- |
| v2.13 internal bridge | Clean up and reconcile the current row-scoped evidence after the RayJoin Goal4376 findings; freeze the current limits honestly. | Internal / corrective planning unless the maintainer explicitly decides how to treat the existing v2.13 source-tree release package. |
| v2.14 formal release | Perform a full cleanup and benchmark-app boost pass; publish only after fresh validation and review. | Formal public source-tree release candidate. |
| V3.0 | Start the planner/device-resident/fused-execution-graph work. | New architecture phase, not a cleanup release. |

If a `v2.13` tag has already been published, it must not be moved or relabeled
without explicit maintainer decision. In that case, the safest wording is
"v2.13 is superseded by the v2.14 cleanup release" rather than "v2.13 was never
public." If the tag has not been published, reviewers should advise whether the
v2.13 package should be demoted to an internal bridge before v2.14.

## 5. v2.13 Internal Bridge Cleanup

The proposed v2.13 internal bridge has one job: make the current state honest
and internally consistent before any stronger release.

Required outcomes:

- Add the Goal4376 RayJoin overlay optimization and caveat to the evidence
  index.
- Repair any v2.13 wording that could imply RTDL hot compute matches RayJoin
  author code.
- Keep RTDL OptiX-vs-Embree claims row-scoped and contract-scoped.
- Separate three columns everywhere they appear:
  - author process wall comparison;
  - RTDL OptiX vs RTDL Embree same-route comparison;
  - exposed traversal / hot-processing evidence.
- Make the RayJoin row explicitly say that near author process wall is not the
  same as author hot-compute parity.
- Leave AMD/Intel GPU work out of the v2.13 story.
- Produce a short internal closeout note: what is validated, what is corrected,
  and what is deferred to v2.14 or V3.0.

Non-goals:

- No retagging without maintainer decision.
- No broad RT-core speedup claim.
- No whole-app speedup claim.
- No RayJoin paper reproduction claim.
- No "all benchmark apps are accelerated by RT cores" claim.

## 6. v2.14 Formal Cleanup and Benchmark-App Boost Release

The proposed v2.14 release should be the formal cleanup and performance-hardening
release before V3.0.

"Boost all benchmark apps" means: for every promoted benchmark app, run the same
discipline of cleanup, route audit, optimization, and explanation. It does not
mean promising that every app will show an RT-core win.

Required v2.14 gates:

| Gate | Meaning |
| --- | --- |
| App inventory clean | The promoted benchmark-app list is current; demoted learner/research apps are not mixed into release claims. |
| Same-contract matrix | Each promoted app has a current OptiX/RT-core route and Embree CPU route when applicable, with the same input contract and explicit partner choice. |
| Partner fixedness | If a continuation needs a partner, the partner is named and held fixed across the comparison or explicitly separated. |
| Best-known route | Each row uses the best known current RTDL route for that backend, not stale unoptimized artifacts. |
| Phase explanation | Each speedup or slowdown has a phase-level explanation; unexplained rows block public wording. |
| Human-scale timing | Rows used for public wording are in meaningful timing ranges where possible, not only tiny microseconds. |
| Native boundary audit | No app-specific native engine names or semantics are promoted as public RTDL primitives. |
| Data movement audit | Avoid unnecessary host/device movement, row materialization, and downloads; remaining movement is documented. |
| Fresh pod packet | NVIDIA pod evidence is current-head, repeatable, and copied into the release packet. |
| Public wording packet | Every public sentence names row, contract, speedup direction, hardware, backend, partner, and caveat. |
| External review | Claude and Gemini review the packet before release; stronger claims need explicit acceptance. |

Suggested v2.14 deliverables:

- `docs/release_reports/v2_14/README.md`
- `docs/release_reports/v2_14/publication.md`
- `docs/release_reports/v2_14/public_rt_vs_embree_comparison.md`
- `docs/release_reports/v2_14/benchmark_app_phase_explanations.md`
- `docs/release_reports/v2_14/rayjoin_author_vs_rtdl_caveat.md`
- `docs/release_reports/v2_14/tag_preparation.md`
- a focused release-validation test set
- a pod artifact manifest
- Claude and Gemini reviews

## 7. V3.0 Target After v2.14

V3.0 should start only after v2.14 closes the cleanup debt. The V3.0 target is
not "add more app-specific kernels." It is:

1. A generic primitive planner and execution graph.
2. Device-resident streams as first-class values.
3. Fused generic continuations for counts, compact positives, face/segment ids,
   grouped reductions, nearest/first-hit summaries, and sparse output.
4. Backend-specific lowering to OptiX/Embree/CUDA partner routes while preserving
   one app-agnostic semantic contract.
5. CUDA-event/Nsight-grade accounting for kernel, copy, build, traversal, and
   host wrapper phases.
6. A policy engine that can say when RT traversal is the right tool and when a
   CUDA partner or CPU path is the honest best path.

RayJoin is an excellent V3.0 diagnostic workload, but it should not become a
native RayJoin engine. The native engine should expose generic capabilities
such as segment-pair intersection, directed segment point-location, compact
candidate streams, device face/segment-id columns, and grouped reductions.
RayJoin topology and map-specific policy should remain app or partner logic.

   rather than a v2.13/v2.14 cleanup item?

5. Does the V3.0 target preserve RTDL's app-agnostic engine rule?
6. What evidence should block v2.14 release if missing?
