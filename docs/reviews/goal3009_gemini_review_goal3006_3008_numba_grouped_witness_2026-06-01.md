## Gemini Review for Goal3006-Goal3008 Numba Grouped Witness Path

**Date:** 2026-06-01
**Verdict:** `accept-with-boundary`

### Summary

This review covers the implementation and validation of generic Numba grouped argmin/argmax operations and their composition for witness selection, as detailed in Goals 3006-3008. The work introduces `grouped_argmin_f64` and `grouped_argmax_f64` as Numba partner continuations and integrates them into a user-facing adapter, `group_argmin_then_global_argmax_partner_columns`. The artifacts demonstrate functional correctness, including handling of ties, missing groups, and various output forms, validated against CPU references from a clean source commit on an NVIDIA L4 pod. All aspects of the work rigorously adhere to a strict claim boundary, explicitly disclaiming release authorization, speedup claims (Numba, RT-core, whole-app), true zero-copy, and app-specific engine behavior. While the functional implementation is robust and well-validated for correctness, the current iteration uses a host-observed compaction step, which is noted as a barrier to performance promotion and true zero-copy. Further work is required for comprehensive performance evaluation and integration into benchmark applications to assess real-world impact.

### Questions To Answer

1.  **Are `grouped_argmin_f64` and `grouped_argmax_f64` implemented as generic Numba partner continuations without app-specific native-engine logic?**
    Yes, `grouped_argmin_f64` and `grouped_argmax_f64` are implemented as generic Numba partner continuations. The code (`src/rtdsl/numba_partner_continuation.py`), associated tests (`tests/goal3006_numba_grouped_argmin_argmax_preview_test.py`), and documentation (`docs/reports/goal3006_numba_grouped_argmin_argmax_preview_2026-06-01.md`) consistently define these operations with generic inputs (`group_ids:int64`, `item_ids:int64`, `scores:float64`) and explicitly state that "No app vocabulary is added to the native engine or the Numba primitive." The `claim_boundary` in the code reinforces that "Numba executes only generic grouped continuation over device arrays; RTDL/OptiX traversal remains separate."

2.  **Does the Goal3007 L4 artifact credibly validate equal-score ties, missing groups, dense outputs, compact outputs, and public adapter use from a clean source commit?**
    Yes, the Goal3007 L4 artifact credibly validates these aspects. The `docs/reports/goal3007_numba_grouped_arg_reducer_l4_pod_2026-06-01.md` report and its corresponding `.json` artifact confirm a "pass" status from a "clean Git checkout" (`source_dirty: []`). The validation includes test cases for a `tie_fixture` and a `large_stream`, explicitly verifying equal-score ties (e.g., "lowest score, then lowest item\_id"), handling of missing groups, correct compact outputs, and accurate dense per-group outputs. The use of the public adapter, `grouped_argmax_f64_partner_columns(..., partner="numba")`, is also validated within these tests, with all results matching the CPU reference implementation.

3.  **Does `group_argmin_then_global_argmax_partner_columns(..., partner="numba")` correctly compose the two generic operations for Hausdorff/RTNN-style witness selection without embedding app semantics?**
    Yes, `group_argmin_then_global_argmax_partner_columns(..., partner="numba")` correctly composes the two generic operations. The implementation in `src/rtdsl/partner_adapters.py` clearly shows sequential calls to `v2_6_numba_partner_continuation_operations.grouped_argmin_f64_partner_columns` and `v2_6_numba_partner_continuation_operations.grouped_argmax_f64_partner_columns`. The report (`docs/reports/goal3008_numba_group_argmin_global_argmax_front_door_2026-06-01.md`) states that "The front door is generic partner continuation only. It does not call RT traversal, does not compute app-specific distances, and does not add native engine logic," ensuring that app semantics are not embedded. Tests (`tests/goal3008_numba_group_argmin_global_argmax_front_door_test.py`) explicitly confirm the absence of app-specific terms in the Numba branch and validate the composite operation against expected witness selection.

4.  **Does the work preserve the user-choice rule for partners and avoid automatic partner selection?**
    Yes, the work rigorously preserves the user-choice rule for partners and avoids automatic partner selection. All partner adapter functions (e.g., `partner_group_count_by_key`, `grouped_argmin_f64_partner_columns`) require an explicit `partner` argument, and the Numba execution path is conditionally invoked when `partner="numba"`. The `v2_6_roadmap()` in `src/rtdsl/v2_6_roadmap.py` explicitly states `"partner_choice_rule": "users_choose_supported_partners_explicitly"`, and all relevant flags like `automatic_partner_selection_allowed` and `automatic_triton_selection_allowed` are set to `False` across code and artifacts, with dedicated validation checks to maintain this boundary.

5.  **Does any report, artifact, or metadata overclaim v2.6 release readiness, Numba speedup, RT-core speedup, whole-app speedup, true zero-copy, or app-specific engine behavior?**
    No, there are no overclaims. All reviewed code, tests, reports, and artifacts consistently and explicitly disclaim all forbidden claims. For example, `src/rtdsl/v2_6_roadmap.py`'s `V2_6_ROADMAP_CLAIM_BOUNDARY` and `validate_v2_6_roadmap` function are designed to prevent such overclaims. The work is consistently presented as a correctness and API-coverage step, still in "preview-status."

6.  **What risks remain before using this path as a recommended benchmark-app implementation?**
    Several risks remain before this path can be considered a "recommended benchmark-app implementation":
    *   **Performance Evaluation:** The current implementation prioritizes correctness and API coverage. It explicitly states it is "not a performance or zero-copy claim" and notes the use of a "host-observed present-group compaction step" as acceptable for correctness but not for performance promotion. Comprehensive, same-contract performance benchmarking against alternative implementations is necessary.
    *   **True Zero-Copy Limitations:** The current approach does not authorize true zero-copy due to the host-observed compaction step. Achieving true zero-copy, if required for a recommended benchmark, would necessitate further engineering effort.
    *   **App-Level Integration and Validation:** While the generic primitives are validated, their integration into specific benchmark applications (e.g., Hausdorff or RTNN-style workloads) still needs to occur. This app-level integration must then undergo its own pod evidence collection to confirm overall functionality and performance characteristics within a complete application context.
    *   **Preview Status:** The operations are explicitly labeled as "preview-status partner continuation." This implies that further maturation, optimization, and stability vetting may be required before they are ready for a "recommended" designation in a benchmark setting.
