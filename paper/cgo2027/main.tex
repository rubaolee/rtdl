\begin{abstract}
Ray-tracing APIs expose fast traversal hardware through a callback protocol whose
correctness depends on more than callback types: build-input topology, payload
layout, lifecycle order, continuation rules, and the identity of the executable
code must agree. Existing Python interfaces make the protocol accessible, but
do not establish that a restricted user program and all of its generated native
components form one admitted execution.

We present \rtdl, a bounded whole-protocol admission design for Python-authored
ray-tracing computations. A typed callback schema, topology-specific trusted
lowerers, executable-identity checks, and lifecycle gates jointly admit a small
set of complete routes rather than accepting callbacks in isolation. The
current artifact supports two stable public constructors and a bounded route
corpus covering triangle, custom-AABB, round-linear-curve, and sphere leaves;
this is not arbitrary Python or topology-generic lowering. A prospective
sealed-snapshot exam selected a sphere any-hit counting composition and produced
two real OptiX launches with 12/12 oracle checks. A separate checker, which does
not import the compiler, validates five generated-code property classes in 20
registered instances, but remains a finite target-structure checker.

Across two NVIDIA GPU generations, we evaluate 160 registered cells containing
20,480 timed samples. At the prepared endpoint, public ahead-of-time \rtdl
median latency is 1.077--1.175$\times$ a direct CUDA/OptiX implementation.
First-result measurements are adverse: post-import \rtdl is
1.560--1.837$\times$ a strong PyOptiX device-continuation baseline by median,
with a 2.377$\times$ worst block. These results delimit the contribution:
bounded protocol admission with near-direct prepared latency on two tasks, not
intrinsic speedup, general lowering, or demonstrated usability.
\end{abstract}

\section{Introduction}

Modern ray-tracing systems expose programmable stages around fixed-function
traversal. OptiX, Vulkan ray tracing, and DirectX Raytracing let programs choose
geometry representations, payload conventions, hit behavior, and launch
topology~\cite{parker2010optix,nvidiaOptix9Guide,khronosVulkanInterfaces,microsoftDXRPAQ}.
This flexibility has enabled non-rendering workloads to use RT cores, but it also
creates an unusual language boundary. A callback can be locally well typed and
still be unsafe or semantically wrong because it is paired with the wrong
build-input kind, stale generated code, an incompatible payload, or an invalid
lifecycle transition.

Python bindings reduce API friction, but they do not eliminate this protocol
problem. A Python user may assemble modules, program groups, shader-binding
records, acceleration structures, streams, and buffers whose compatibility is
represented only by convention. Conversely, a compiler that validates a
restricted callback body but delegates the surrounding protocol to hand-written
wrappers has proved only local compilation. The research question in this work
is therefore:

\begin{quote}
Can a restricted Python system admit an entire bounded ray-tracing protocol,
including generated native code, executable identity, and lifecycle state,
while retaining prepared-execution latency close to direct CUDA and OptiX?
\end{quote}

We answer for a deliberately narrow domain. \rtdl accepts a typed, restricted
callback representation and maps admitted programs to compiler-owned,
topology-specific lowerers. It records the source, PTX, ABI, and native symbols
that constitute an executable route; checks lifecycle transitions before
launch; exposes status before output; and supplies an independent offline
checker for selected generated-code properties. The canonical plan is a
non-executable specification. Executable lowering remains in the trusted
topology-specific implementation. This distinction is central: our evidence
does not establish an arbitrary callback compiler.

This paper makes four contributions:
\begin{enumerate}[leftmargin=*,itemsep=1pt,topsep=2pt]
  \item A \emph{whole-protocol admission model} that binds callback effects,
  topology, ABI, executable identity, and lifecycle state into one bounded
  route decision.
  \item A concrete Python-to-OptiX implementation with two stable public
  constructors, four leaf kinds in the bounded route corpus, and explicit
  topology-specific lowerers in the trusted computing base (TCB).
  \item A finite, compiler-independent checker and mutation evidence that expose
  what is checked, what remains trusted, and where the current guarantees stop.
  \item A preregistered two-generation evaluation of two tasks: prepared public
  latency is 1.077--1.175$\times$ Direct, while adverse first-result and
  incomplete-receipt results constrain the claim.
\end{enumerate}

\section{The Protocol Mismatch}

\subsection{Why callback typing is insufficient}

A ray callback runs inside a protocol distributed across host and device code.
Its legal effects depend on its role: an any-hit callback may ignore or
terminate an intersection, whereas a miss callback cannot. Its payload fields
must agree with every producer and consumer. Its program group must match the
acceleration-structure leaf kind. The launch must occur only after module,
pipeline, shader-binding-table, geometry, and output state have been prepared.
Finally, the code checked by the compiler must be the code loaded by the runtime.

These are related to typestate, interface automata, and session-style protocol
reasoning~\cite{strom1986typestate,deAlfaro2001interfaceAutomata,honda2016multiparty},
but the FFI and generated-code boundary adds an identity problem familiar from
linking and foreign interfaces~\cite{furr2005ffi,patterson2017linkingTypes}.
Table~\ref{tab:obligations} summarizes the obligations used here.

\subsection{A concrete semantic-ABI failure}

Consider two acceleration-structure primitives at physical positions 0 and 1
whose application identifiers are 10 and 20. Queries 100 and 101 should emit
the pairs $(100,10)$ and $(101,20)$. In an executed defective route, the
intersection callback instead placed the primitive position in attribute slot
zero. The any-hit callback consumed that slot as an application identifier and
returned $(100,0)$ and $(101,1)$. Every value remained a valid \texttt{u32};
the acceleration structure, module, program groups, pipeline, shader binding
table, and launch were legal. Typed OptiX and construction routes reached
launch and returned the wrong rows.

The defect is not a machine-type error but a disagreement over what the bits
mean. In \rtdl, a fixed route contract says that attribute slot zero denotes an
application identifier, while the compiled target description records the
actual row source. Admission compares these authorities and rejects the
disagreement before launch. The system does not infer which objects should
match, and an application oracle is still necessary. Admission instead rejects
the broken producer--consumer agreement independently of whether a test input
happens to make primitive positions and identifiers differ.

\subsection{Failure model}

We distinguish four outcomes. \emph{Reject} means admission fails before a
launch. \emph{Status failure} means execution reports failure and output is not
published. \emph{Wrong output} means a worker reports success but an independent
oracle disagrees. \emph{Unverified output} means a value exists without the
required receipt or oracle evidence. The distinction prevents a status gate
from being described as numerical correctness and prevents a generated plan
from being described as an executable lowering.

The implementation has a double-fault caveat: teardown failure while a provider
releases retry ownership can replace a primary exception. No
public output is then released, and we did not observe this event, but the
diagnostic provenance can be degraded. Similarly, the fork guard is enforced
for Python-managed use; bypassing the public layer and invoking native state
after a fork is outside the admitted contract.

\section{Bounded Language and Admission}

\subsection{Callback representation}

The source language is restricted Python, not arbitrary Python. Source is
parsed through an AST allowlist and is not imported or executed for discovery.
The front end resolves declared immutable records, frozen constants,
same-unit acyclic helpers, and selected intrinsics, then produces canonical
typed IR. Deserialization reconstructs typed objects and reruns verification;
serialized IR is not itself an authority. Table~\ref{tab:ir} summarizes the
representation.

The current resource contract admits at most 32 payload slots and eight
attribute slots, trace depth one, callable depth zero, bounded helper depth, and
statically bounded iteration. The numeric policy requires explicit binary32
behavior and fail-closed handling of prohibited integer overflow and nonfinite
effects. These are language and resource checks; they do not prove that a
chosen ray encoding computes the intended application function.

\subsection{Role-indexed effects}

Seven language roles participate in an admitted unit. \texttt{bounds} runs
during preparation; \texttt{make\_ray} and \texttt{finalize} are language
leaves invoked by a trusted ray-generation wrapper; and \texttt{intersection},
\texttt{any\_hit}, \texttt{closest\_hit}, and \texttt{miss} map to target-stage
behavior. User code cannot invoke raw traversal. Instead, each role returns one
typed effect from a role-specific set: bounds returns an AABB, ray construction
returns a trace request, intersection returns hit or no-hit, hit callbacks
return payload plus continue/ignore/terminate control, miss returns payload,
and finalize returns an output.

Topology makes these requirements relational. Custom AABBs require bounds,
ray construction, intersection, miss, finalize, and at least one hit role.
Built-in triangles forbid bounds and intersection because hardware owns them,
but retain ray construction, miss, finalize, and at least one hit role. An
any-hit role also requires an explicit delivery and continuation contract; the
presence of that declaration does not prove order independence for arbitrary
callback logic.

\subsection{Fail-closed judgments}

Expression checking derives $\Gamma \vdash e : \tau$. Statement checking also
returns the output environment, all-paths-return bit, conservative static work,
and observed effects:
\begin{equation}
  \Gamma;r \vdash s \Rightarrow \langle \Gamma',q,n,\epsilon\rangle .
\end{equation}
For each role $r$, verification enforces its exact signature and
\begin{equation}
  M \vdash F_r : \epsilon
  \quad\text{with}\quad
  \epsilon \subseteq \mathsf{AllowedEffects}(r).
\end{equation}
Names are single-assignment except for type-preserving updates inside static
loops; loop locals cannot escape; both non-returning branches define the same
typed names; and every role/helper path returns. Whole-unit checking validates
schema/source identity, acyclic records and helpers, numeric and resource
budgets, role cardinality, topology, linkage, and required external physical
authority:
\begin{equation}
  \mathcal{G};\mathcal{R} \vdash Q \Downarrow
  \mathsf{Verified}(h_{\mathrm{IR}},h_{\mathrm{effects}}).
\end{equation}
Here $\mathcal{G}$ is an out-of-program geometry authority and $\mathcal{R}$ is
the compiler-owned role topology. The judgment is explanatory notation for
implemented checks, not a mechanized soundness theorem.

Admission is conjunctive. A route is accepted only if its schema is valid, its
roles permit all effects, its semantic and physical ABIs agree, a trusted
lowerer exists for its topology, the generated executable identity is bound,
and the runtime lifecycle can reach the prepared state. Failure of any one
predicate rejects the route; there is no ``best effort'' projection into a
nearby executable.

\subsection{Plan versus executable lowering}

The canonical planner normalizes the admitted schema and emits a declarative
plan. That plan is intentionally marked non-executable. It does not synthesize
arbitrary CUDA or OptiX callbacks. Instead, an accepted route names a
compiler-owned, topology-specific lowerer and wrapper. The lowerer emits source
and PTX, binds native symbols, constructs the program groups and shader-binding
table, and records their identities. This design supplies a common admission
surface while keeping concrete backend knowledge visible in the TCB.

The distinction addresses a common overclaim. Sharing schema validation and
lifecycle machinery does not imply that the device implementation is generic.
In the prospective composition described in Section~\ref{sec:prospective}, the
new sphere route required approximately 2,635 lines of topology-specific code
and 28 modified compiler lines. That is evidence that the framework can admit
a new trusted route without changing three sealed shared files, not evidence
that a new topology is lowered automatically.

\subsection{Executable identity and lifecycle}
\label{sec:lifecycle}

The system binds hashes and shape metadata for generated source, PTX, ABI,
native provider symbols, and the public route. Runtime preparation checks the
binding before execution. The admitted lifecycle is:

\begin{center}
\small
static verify $\rightarrow$ materialize/bind $\rightarrow$ prepare
$\rightarrow$ execute/status gate $\rightarrow$ output $\rightarrow$ receipt.
\end{center}

The final public path checks native and compact status synchronously and the
experiment checks every returned output against an oracle before declaring a
worker successful. It does \emph{not} rehash files from disk on every launch.
Moreover, the original design goal of a detailed receipt for every timed
execution is not met: 4,096 timed executions in the main \rtdl arm are
accompanied by 32 separate post-loop detailed diagnostic receipts. We therefore
claim synchronous status and output gating, not per-execution detailed receipt
coverage.

The implementation uses Python for the public authoring surface and C++/CUDA
with OptiX for trusted lowering and execution. This is a compiler/runtime
prototype rather than a pure-Python implementation. Table~\ref{tab:scope}
separates stable public constructors from the broader bounded route corpus.

The route corpus is broader than the stable facade but narrower than OptiX.
Unsupported geometry options, motion modes, callback combinations, and payload
shapes remain outside the contract. Extension requires adding or auditing a
trusted lowerer; a matching schema alone is insufficient.

\section{Evaluation}

We ask four questions: (1) do whole-protocol mutations reach the intended
gates; (2) can a sealed shared framework admit one selected composition; (3)
does a separate checker validate concrete generated artifacts without trusting
the compiler's own projection; and (4) what performance cost does the public
route impose at registered endpoints?

\subsection{Earlier liveness and residual evidence}

For two accepted fixed contracts, 19 single-leaf mutations exercised 19/19
expected gates: seven role-and-effect, one semantic-ABI, seven physical-ABI, two
continuation, and two identity mutations. This denominator is limited to those
two contracts and those mutations; it is not combined with the later
composition or checker experiments.

We also examined typed residual failures against OptiX and OWL-style execution
paths~\cite{nvidiaPyOptix,nvidiaOWL}. Three residuals produced complete
wrong-output witnesses. A fourth supplied only a partial status-gated
continuation/completeness witness. Checked executable identity adds supporting
evidence. These are concrete failure observations, not five proved guarantees
or general soundness theorems.

\subsection{Sealed-snapshot composition exam}
\label{sec:prospective}

Before revealing a future public randomness pulse, we fixed an author-defined
challenge table of ten rows: seven built-in four-role rows and three custom
six-role rows. All rows used already-supported primitive families; the three
continuation variants all used a per-query count relation. The round-linear-curve
any-hit-terminate row remained an eligible candidate; it was not selected. The
pulse selected
\nolinkurl{builtin_sphere::any_hit_count_continue_u64_per_query}.

The artifact's private custody record identifies the exact sealed historical
source. Implementation changed no bytes in the three frozen schema, admission,
and lifecycle files. The resulting route
performed two true OptiX launches and passed 12/12 rational-oracle rows. The
result demonstrates framework-level reuse of admission, identity, and lifecycle
machinery for this selected composition. It does not establish an unbiased new
application: the authors defined the challenge domain, every row recombined
known primitives and topologies, and the selected route required substantial
new topology-specific implementation.

\subsection{Independent finite checker}

The offline checker imports no \rtdl module and rejects compiler-supplied
projections as authority. It independently reads generated source, PTX/ABI
metadata, symbols, and receipts. Across three route groups and four modes, it
applied five property classes 20 times using 15 unique mutations. It also
partially evaluates generated target structure rather than trusting labels in
the compiler output.

This checker is finite, not a verifier for arbitrary device control flow.
During review, an out-of-authority in-memory probe inserted an unconditional
early return and still passed selected effect/status helper checks. The result
therefore supports specialized target-structure validation only. General
control-flow, numerical, and refinement soundness remain open; tools such as
GPUVerify illustrate the substantially stronger proof obligation~\cite{betts2012gpuverify}.

\subsection{Performance methodology}

We measured two exact tasks. \emph{Relation} uses 4,096 objects and 4,096
queries, returns 4,096 canonical u32 pair rows, and performs two true OptiX
traversals. \emph{Triangle} uses 16,384 primitives and 16,384 queries, performs
one true traversal, and returns the checked scalar 65,530.

Five arms isolate different boundaries:

Each generation has eight blocks, two tasks, and five arms: 80 cells, with 128

The registered primary criterion was prepared A/D median $\leq1.20$. There was

The registered A/E prepared criterion was $\leq1.05$; C/B competence used

\section{Programming Responsibility and Generality}

The design separates three responsibilities. Users provide bounded callback
intent and application data. Shared \rtdl machinery validates schemas,
cross-role effects, ABI compatibility, executable identity, and lifecycle.
Trusted per-topology lowerers remain responsible for concrete CUDA and
OptiX code generation and binding. The runtime refuses to publish output when its
status gates fail, while experiments may add application-level oracles.

This decomposition is reusable beyond the present implementation. A system
crossing from a managed language to an accelerator can adopt whole-protocol
admission: name roles and effects, make semantic and physical ABI explicit,
bind checked artifacts to loaded artifacts, and gate state transitions. The
same principles can inform other Python GPU systems, shader languages, and
foreign-function interfaces. What does not automatically transfer is the
topology-specific lowerer or the finite checker vocabulary. Those components
must be re-established for each backend.

\section{Related Work}

OptiX established a programmable ray-tracing pipeline~\cite{parker2010optix},
and current OptiX, Vulkan, and DXR interfaces expose explicit pipeline and
shader-group contracts~\cite{nvidiaOptix9Guide,khronosVulkanInterfaces,microsoftDXRPAQ}.
PyOptiX-style bindings and OWL improve host-language access and construction
ergonomics~\cite{nvidiaPyOptix,nvidiaOWL}; our focus is not replacing those APIs
but admitting a bounded cross-stage protocol and binding it to executable
identity.

Shader and heterogeneous programming systems provide richer compilation
abstractions. Slang's capability system and modular shader work address
composition and target restrictions~\cite{slangCapabilities,he2017shaderComponents,he2018slang}.
Dr.Jit, LuisaRender, and CrossRT explore staged or cross-language generation
for graphics and simulation~\cite{jakob2022drjit,zheng2022luisa,frolov2024crossrt}.
\rtdl differs in its narrow emphasis on admitting the surrounding RT protocol,
but its current topology-specific lowerers are less general than those systems'
broader compilation ambitions.

The protocol framing draws on typestate and interface theories
~\cite{strom1986typestate,deAlfaro2001interfaceAutomata,honda2016multiparty} and
on typed linking and FFI work~\cite{furr2005ffi,patterson2017linkingTypes}. Our
finite artifact checker is empirical and structural; it should not be confused
with formal GPU verification such as GPUVerify~\cite{betts2012gpuverify}.

\section{Artifact}

The candidate artifact is an evidence-only, nine-member archive generated from
the final frozen tooling snapshot. It contains an anonymous evidence projection,
summary, manifest, documentation, dependency/component inventory, and a Python
verifier using only the standard library. Private provenance and export receipts
remain in the separate custodial record and are not distributed in the anonymous
archive. The projection records 160 formal cells, 20,480 steady samples, 1,024
A-only instrumentation endpoints, 20 AOT samples, and eight competence records.

Two clean exports were byte-identical. Replays in two fresh directories, one
with spaces, passed under isolated normal and optimized Python modes. The archive bundles no
third-party source, binary, dataset, CUDA/OptiX header, driver, key, or raw GPU
archive. It therefore supports offline verification of the submitted evidence,
not GPU rerun, product installation, or full reconstruction of private historical
authorities. CUDA, OptiX, drivers, and GPU hardware are external requirements
for new execution.

\section{Threats to Validity}

\paragraph{Construct validity.}
Prepared A/D measures the public steady path after setup; it does not measure
interactive authoring, cold compilation, or first use. Direct D is a useful
lower-bound implementation, not an application framework. Strong C is
contract-equivalent at the output boundary but is neither byte-identical nor
operation-identical to A. A-only instrumentation does not qualify other arms.

\paragraph{Internal validity.}
Both tasks were used during system adaptation and tuning; they are not unseen
confirmatory workloads. The implementation-entry endpoint was revised after an
adverse observation, and both first-result endpoints include import and lifecycle
effects. We preserve those outcomes rather than reinterpret them as a pass.
The provider double-fault and Python-only fork boundary remain documented risks.

\paragraph{External validity.}
Measurements cover two consumer NVIDIA generations and two exact tasks. We do
not compare raw latency across machines. The prospective challenge domain was
author defined, used known primitive and topology ingredients, and selected one
composition. There is no independent human authoring study, no prevalence
measurement, and no evidence for arbitrary Python or arbitrary Callback IR.

\paragraph{Implementation trust.}
Approximately 2,635 lines of new topology-specific code were required for the
selected sphere route. These lowerers and wrappers are in the TCB. The
independent checker covers finite target structures and missed an
out-of-authority early-return probe for selected helper checks. Detailed
per-execution receipts were not produced for the 4,096 timed A executions.

\paragraph{Artifact scope.}
The anonymous projection is derived evidence, not the raw private archives. Its
verifier checks internal identities, counts, registered formulas, and disclosed
rows, but cannot independently recreate GPU runs or historical custody. Private
provenance remains available for confidential audit.

\section{Conclusion}

\rtdl demonstrates bounded admission for a complete ray-tracing protocol,
instead of checking callbacks in isolation. Shared schema, identity, and lifecycle machinery
supports two stable public constructors and a four-leaf bounded corpus, while
executable lowering remains topology-specific and trusted. Mutation,
sealed-snapshot composition, and finite-checker evidence exercise this boundary
without establishing general compiler soundness.

For two exact tasks on Ada and Ampere GPUs, the prepared public route costs
1.077--1.175$\times$ direct CUDA/OptiX latency by median. First-result results
are materially worse, with post-import A/C medians up to 1.837$\times$ and a
2.377$\times$ worst block. The contribution is bounded whole-protocol admission
with near-direct prepared latency and explicit TCB, receipt, generality, and
lifecycle limits. Removing those limits is the next research problem.
