# Goal5838 preregistration: generic core and prospective topology exam

Date: 2026-09-02

Status: `PREREGISTERED_BEFORE_GENERIC_CORE_MUTATION`

## Scientific question

Can RTDL replace concrete-family dispatch with one schema-driven admission,
compilation-plan, provider-binding, and public lifecycle core, freeze that core,
and then execute an independently selected new callback topology without
changing any frozen-core byte?

## Repair-before-freeze rule

Stages A and B are engineering. Any defect found before the generic-core seal
must be investigated and may be repaired. Such a defect is not a prospective
failure. There is no deadline-based or attempt-count-based engineering failure.

The frozen core must contain no application-name dispatch and no dispatch on
the current concrete protocol constructors. Geometry- and target-specific work
belongs in providers; application semantics belongs outside the core.

## Challenge selection

The actual topology is selected only after the generic-core file inventory and
hash seal exist. Selection must be performed by an external reviewer from a
complete, precommitted challenge table or by another owner-approved independent
procedure whose outcome was unavailable during core implementation. Project
authors may define admissibility rules but may not choose a convenient row
after seeing core behavior.

Temporary unavailability of an independent selector leaves Stage C pending; it
is not a scientific failure and does not authorize an author-selected fallback.

## Allowed post-selection work

After challenge revelation, unlimited engineering iterations are allowed in:

- the selected protocol instance and restricted Callback IR;
- package-external or provider-specific implementation modules;
- application-owned input/oracle code;
- tests, runners, reports, and evidence tooling; and
- build/environment repair that does not alter frozen-core bytes or semantics.

Finding an ordinary implementation bug in these layers is not a failure. The
team must diagnose and repair it before drawing a conclusion.

## Only scientific failure condition

The prospective attempt fails only when all of the following hold:

1. the generic-core seal predates independent challenge revelation;
2. the selected challenge satisfies the preregistered admissibility rules;
3. the team has attempted the challenge through every allowed extension layer;
4. a required semantic or execution capability cannot be expressed without a
   byte change to the frozen generic core; and
5. the necessity of that core change is demonstrated by a minimal witness and
   hostile internal review.

A platform outage, missing Pod, temporary toolchain defect, ordinary provider
bug, unavailable independent selector, or submission deadline is `PENDING` or
`BLOCKED`, never a scientific failure.

## Success condition

One independently selected topology must pass schema admission, Callback-IR
verification, provider binding, public `compile -> materialize -> prepare ->
execute -> close`, an independent CPU oracle, hostile cases, and a true-GPU
execution receipt with zero frozen-core byte changes after selection.

Passing Goal5838 establishes one bounded prospective frozen-core topology
result. It does not establish arbitrary Callback-IR execution, universal
provider portability, usability superiority, or application correctness.
