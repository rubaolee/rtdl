### 2. Does the evidence prove it missed the same-run writer performance gate?

**Yes.**
The performance gate dictates that the path-split adapter writer must run faster than the same-run plain writer. The observed timings from [summary.json](file:///C:/Users/Lestat/Desktop/work/rtdl_v0_4_release_prep_review/history/internal_docs/goal4940_pod_artifacts/summary.json) are:
- **Existing Plain Writer Time (`output_chain_write_sec`):** `2.559022s`
- **Generic Path-Split Adapter Writer Time (`output_chain_write_sec`):** `4.175830s`
- **Timings Delta:** Slower by `1.616808s` (+63.18%).

The route also resulted in an increase in total elapsed application time from `6.135681s` to `7.753231s`. The gate was decisively missed.

---

### 3. Is the interpretation correct that the host-columnar Python path-split/materializer is semantically right but too slow?

**Yes.**
The implementation successfully generated byte-identical output, confirming the conceptual boundary is semantically correct. However, executing the path-splitting logic and row-buffer materialization in Python/NumPy-host code introduces prohibitive overhead.
According to the breakdown in [goal4940_rayjoin_path_split_adapter_pod_gate_2026-07-04.md](file:///C:/Users/Lestat/Desktop/work/rtdl_v0_4_release_prep_review/history/internal_docs/goal4940_rayjoin_path_split_adapter_pod_gate_2026-07-04.md):
- **Materialization (`path_split_materialize_map0 + map1`):** `2.388547s`
- **Formatting (`path_split_format_map0 + map1`):** `1.354805s`
These two steps alone consume `3.743352s` (approximately 90% of the total path-split writer budget). Doing grouping, slicing, and index manipulation in a Python host loop dominates the execution time.

---

### 4. Is it correct to revert the experimental app wiring and retain only the generic Goal4939 API plus reports/artifacts?

**Yes.**
Because the path-split adapter failed the performance gate, keeping the experimental wiring in the default app pipeline would introduce a performance regression for RayJoin. Reverting the experimental edits ensures the performance baseline is maintained. Retaining the generic Goal4939 API [assemble_grouped_path_split_records](file:///C:/Users/Lestat/Desktop/work/rtdl_v0_4_release_prep_review/src/rtdsl/output_assembly.py#L286-L302) and [materialize_grouped_output_row_buffer](file:///C:/Users/Lestat/Desktop/work/rtdl_v0_4_release_prep_review/src/rtdsl/output_assembly.py#L252-L260) inside [output_assembly.py](file:///C:/Users/Lestat/Desktop/work/rtdl_v0_4_release_prep_review/src/rtdsl/output_assembly.py) is correct, as it preserves a generic, domain-neutral prototype for potential compiled or native materialization routes.

---

### 5. Is it correct that no RayJoin speedup or public performance claim is authorized?

**Yes.**
Since the experimental path-split adapter route did not achieve a speedup and was reverted, there is no authorized basis for any public performance or speedup claims regarding this route.

---

### 6. Is the next implementation, if any, a compiled/native generic path-split materializer rather than more app-adapter micro-patching?

**Yes.**
The bottleneck lies directly in the execution speed of the host-columnar Python materialization phase. Further micro-patching at the Python application-adapter layer cannot bypass the inherent cost of Python-host loop processing on hundreds of thousands of rows. The next step must compile the generic logic (e.g., using a compiled backend like Cython/C++/CUDA) or process it natively on-device to bypass the CPU-host row-buffer formatting step entirely.
