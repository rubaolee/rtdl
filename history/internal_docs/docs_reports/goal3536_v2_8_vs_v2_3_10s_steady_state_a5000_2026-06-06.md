## Purpose

Goal3536 answers the reader-facing concern that the previous v2.8-vs-v2.3 table used many sub-millisecond rows. The new harness stretches each comparable OptiX row toward a 10-second measured hot-query window where the app exposes a safe repeat knob, while keeping setup and validation separate from the primary metric.

The harness deliberately does not fake evidence. Rows without a repeat hook, or rows whose repeat hook would create unreasonable wall time, are marked partial diagnostics.

## RayDB Count vs Sum

The long-run packet changes the RayDB reading. In the earlier compact Goal3524 table, RayDB count was near parity while RayDB sum appeared to show a `7.2x` v2.8 win. Under the calibrated 10s protocol, both rows settle near parity:

- grouped count: `0.973x`
- grouped sum: `0.998x`

The correct interpretation is:

- Count is a tiny grouped cardinality query. Both v2.3 and v2.8 are already near the dispatch/launch floor, so large speedups are not expected.
- Sum is the heavier value-column reduction. v2.8 did improve the design direction, but the earlier short packet over-amplified a transient v2.3 slow measurement. The long-run result does not support a stable 7x RayDB sum claim.
- RayDB should therefore be described as a correctness/primitive-first resident grouped-reduction capability, not a current headline speedup row.

## Engineering Conclusions

1. The 10s protocol is feasible for rows with real repeat hooks.
2. The previous sub-ms table was too noisy for strong performance conclusions.
3. The strongest current v2.8 wins in this exact v2.3 comparison are modest, not dramatic.
4. Barnes-Hut remains a real weak row in this contract.
5. Hausdorff, spatial RayJoin, robot collision, Barnes-Hut, and LibRTS need app-level repeat hooks or more resident prepared-query loops before they can produce final 10s steady-state evidence.
6. The next performance task should not be another table; it should add repeat-hook/resident-loop support to the five partial rows, then rerun Goal3536.
