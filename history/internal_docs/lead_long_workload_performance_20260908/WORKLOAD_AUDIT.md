## Immediate recommendation

**Start with one complete RT-2A1 triangle-counting computation on the existing real-graph ladder: `com-dblp`, then `cit-Patents`, then `soc-LiveJournal1`. Qualify scale on the competent public PyOptiX owner before comparing the repair.** Select a graph whose single prepared, full-graph computation is at least one second, preferably 1–10 seconds. This is a candidate-selection procedure, not a claim that a specific larger graph has already met that duration.

Each logical computation must consume all distinct graph edges, execute every deterministic source-domain segment exactly once, and return the checked whole-graph count. Segmentation is a memory technique; looping the same small graph, truncating its segment iterator, or shrinking segment capacity merely to increase overhead does not establish a large task. Keep the existing RT-2A1 algorithm on both sides. Do not choose the slower RT-1A2 baseline to reach one second.

`com-dblp` is a correctness/regression anchor, not an already qualified long prepared workload: the prior strong PyOptiX prepared median is **0.437096 s**. Its **1.312973 s first-execute** includes first-use effects, and its **3.508170 s complete** includes preparation. Neither is evidence that its prepared graph computation lasts one second.

### Triangle memory and semantic traps

- The [CSR builder:39](/Users/rl2025/rtdl_v4_restricted_python_design/examples/current/research_benchmarks/triangle_counting/segmented_rt_graph.py:39) memory-maps little-endian signed-int32 edge pairs, but allocates degree/remap tables and global unique-edge arrays. It is O(max vertex ID + E), **not constant host memory**. [Lines 96–100](/Users/rl2025/rtdl_v4_restricted_python_design/examples/current/research_benchmarks/triangle_counting/segmented_rt_graph.py:96) reject excessive sparse-ID extent. `np.unique` and its temporary copies can exhaust RAM before any GPU launch. Check actual host RSS and temporary-disk space; the source file size is not the peak memory estimate.
- `_source_partitions` [line 215](/Users/rl2025/rtdl_v4_restricted_python_design/examples/current/research_benchmarks/triangle_counting/segmented_rt_graph.py:215) bounds two-hop relation rows and directed edge rows. A high-degree single source can still fail `SINGLE_SOURCE_DIRECTED_EDGE_BOUND_EXCEEDED`; only its oversized two-hop relation is further split at [line 284](/Users/rl2025/rtdl_v4_restricted_python_design/examples/current/research_benchmarks/triangle_counting/segmented_rt_graph.py:284). Retain the failure instead of silently omitting that source.
- Keep the initial 1,000,000-row bound on **both** arms. Count deterministic segments without GPU using the existing `count_segmented_rt_graph_segments` [line 506](/Users/rl2025/rtdl_v4_restricted_python_design/examples/current/research_benchmarks/triangle_counting/segmented_rt_graph.py:506), after a valid CSR exists. This is structural planning, not a time prediction. A segment has several f64 host/device columns, U64 keys/weights, packed f32 geometry, GAS temporary/output storage and runtime result state; its row cap does not itself prove VRAM fit.
- RT-2A1 [geometry:383](/Users/rl2025/rtdl_v4_restricted_python_design/examples/current/research_benchmarks/triangle_counting/segmented_rt_graph.py:383) uses centered integer-like coordinates and width `eps=0.2`, then the baseline casts to f32 at [triangle_owner.py:228](/Users/rl2025/rtdl_v4_restricted_python_design/experiments/v4_paper_apps_pyoptix/triangle_owner.py:228). Larger IDs can make offsets collapse in f32 even when U32 cardinality checks pass. The two proposed graphs have fewer than 4.85M source nodes; do not generalize their numeric safety to arbitrary larger graphs. Validate nondegenerate consumed geometry and the full exact oracle at the chosen scale.
- The iterator supports `start_segment_id`/`stop_segment_id` [line 419](/Users/rl2025/rtdl_v4_restricted_python_design/examples/current/research_benchmarks/triangle_counting/segmented_rt_graph.py:419). It resizes the eligible cell array and cycles only **four** barycentric weight patterns ([lines 137–143](/Users/rl2025/rtdl_v4_restricted_python_design/scripts/goal5776_prepare_particle_mesh.py:137)). Raising that constant sufficiently repeats the same positions, so it is not an adequate independent-query scale generator. The first-batch [adapter:52](/Users/rl2025/rtdl_v4_restricted_python_design/experiments/v4_paper_apps_pyoptix/particle_adapter.py:52) and [dynamic input:104](/Users/rl2025/rtdl_v4_restricted_python_design/experiments/v4_paper_apps_pyoptix/particle_adapter.py:104) also hard-bind the formal 5,000-query shape. The lower-level owner has a `ParticleProblemShape`, but the formal adapter does not automatically expose variable scale.

If pursued, define a **new, explicitly generated one-transition ensemble** over the real mesh, with distinct deterministic strict-interior positions and independently computed U32×3 outputs. A candidate ladder such as 1M, 5M, 20M distinct queries is only a feasibility proposal; none has been generated, validated or timed here. It requires new input construction, manifests and adapter shape support. Do not claim these positions are recovered author random-particle bytes, and do not call independent one-step queries a temporal simulation. At large Q the query/output arrays alone are at least 40Q bytes per full copy, with multiple host/device copies and much larger potential Python-object overhead; query generation and topology-oracle computation must be chunked and bounded. Increasing mesh copies, ray `tmax`, or any-hit work while leaving the native-closest-hit baseline unchanged is not an equivalent way to scale the same task.

## LibRTS: retain for repair/regression; poor first choice for the one-second target

[load_librts:167](/Users/rl2025/rtdl_v4_restricted_python_design/experiments/v4_paper_apps_pyoptix/inputs.py:167) fixes the `parks` cache, two `*_100000.wkt` query files, exact 100,000 cardinality and the two scalar oracles. The data-bundle builder includes only those two query files ([bundle builder:78](/Users/rl2025/rtdl_v4_restricted_python_design/scripts/goal5776_build_real_scale_data_bundle.py:78)). This pass found no already retained larger real-query batch or matching oracle. The small benchmark's random fixture generator is not evidence of a larger real parks workload.

At unchanged per-query behavior, 0.23 ms per 100,000 queries suggests a gap of roughly 4,300× to one second—hundreds of millions of queries. This is **order-of-magnitude triage, not a scaling prediction**. The current loader builds Python tuples and the baseline re-materializes arrays in `normalize_queries` ([librts_owner.py:108](/Users/rl2025/rtdl_v4_restricted_python_design/experiments/v4_paper_apps_pyoptix/librts_owner.py:108)); this can fail host memory long before U32 query-count limits. Hundreds of millions of four-f32 query columns already require multiple GB before object overhead, copies, count buffers and the 11.5M-box GAS.

Do not tile the same 100,000 queries, duplicate the index, or switch from `range_contains` to `range_intersects`/collection merely to obtain a second. A genuinely new dense spatial workload may be legitimate if independently motivated, but it needs newly bound real inputs, the unchanged intended predicate, f32-aware oracle, and a competent baseline—not the old hardcoded counts. Keep point/range count repair in the portfolio even if it remains sub-second. A total larger than one second due solely to WKT parsing or GAS setup does not answer the requested long prepared-computation question.

## Minimal selection and measurement requirements

1. Preserve the old 3/9 campaign and its adverse ratios verbatim. Register a new source/config/data identity and keep old/new input results separate. Do not turn this limited scale audit into authorization to claim nine current benchmarks.
2. Qualify the **competent C implementation's single logical computation** on the finite real-graph ladder. Preserve every tried candidate's correctness, resource and timing outcome; choose by baseline duration and feasibility, not by the most favorable A/C ratio. An otherwise valid graph above 10 s may remain useful if the experiment budget permits; do not pad or truncate it to fit the preferred window.
3. For the whole-domain endpoint, start from the same raw in-memory graph edge relation and include orientation/filtering/deduplication/CSR, geometry construction, method preparation, complete checked output and close. If disk loading is excluded, state that explicitly. Keep a separate prepared whole-graph endpoint. The old loader places substantial graph preprocessing before its `complete` timer ([worker:571](/Users/rl2025/rtdl_v4_restricted_python_design/scripts/v4_paper_apps_pyoptix_worker.py:571)); merely reusing that timer does not produce a full-domain endpoint.
4. Keep one-second qualification separate from import, compilation and first-use effects. Record directly observed preprocessing/geometry/GAS/traversal/reduction/validation phases where available, without subtracting them from the public wall result or adding overlapping phases. A ≥1 s app-stage wall observation alone must not be described as ≥1 s GPU traversal.
5. Hold algorithm, full output, exact graph transformation, numeric rules and logical segment coverage equal. Keep strong C's reuse, flags and compact device reduction. For deploy/setup comparisons, disclose and either match source-compilation lifecycle or report it separately; the prior C PTX was precompiled while A Particle/graph compiled inside setup.
6. Keep synchronous status and output-oracle checks and explicit identity/capacity checks. Do not hide their cost or reuse the old detailed-receipt shortfall as permission to claim full validation without measuring it. An OOM, precision mismatch or missed source partition rejects the candidate/result; it is not a partial success.

Recommended execution order: **Triangle real-graph scale and V4 lifecycle repair first; retain Particle/LibRTS small-input regressions; consider a newly generated large Particle ensemble only as a separately declared second task.** No existing retained prepared observation in these four units already establishes the owner's ≥1 s strong-baseline target.
