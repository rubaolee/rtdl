## 2. 要完成的事及硬验收

目标是在真实应用计算上，证明新增语言机制可以以可接受的成本提供。功能成功不关闭性能问题；运行超过一秒也不自动关闭性能问题。

**本轮工程验收目标沿用已有性能目标：各有效主单元 paired A/C 中位数 ≤1.20，所有八个 block ≤1.35。** 这是整改完成目标，不是允许报道的筛选门槛；未通过、超时、OOM、错误输出和性能回退全部保留。没有达到目标时只能报告哪些单元已修复、哪些仍不具备性能可用性，不能宣称整体性能问题已解决。

1. 正确性：相同完整输出与事先固定的独立 oracle 一致，公开检查、生命周期和失败语义保留。

## 3. 什么算真实长任务

一秒标准针对强 C 完成的一次有实际含义的计算，不能以 RTDL 很慢作为达标理由。增加真实数据规模、不同查询数量、应用本来需要的依赖步骤或完整算法工作；不得重复相同小输入、空转、添加 sleeps、额外串行化或减慢 C 来凑时长。

框架初始化、编译和实验 oracle 耗时单独列出，不能仅因这些超过一秒就声称有长计算。算法必需的图定向、建树、几何构造和结果物化属于完整任务，但必须另报执行阶段，防止共同准备开销掩盖执行差距。至少要有实质计算较长的应用行。

选规模只使用任务定义、已存在的输入顺序、C 的可行性/耗时和显存约束；不得查看 A/C 输赢后挑规模。保留探索记录，正式规模冻结后不得删掉 A 的失败行。正式 C 因波动略低于一秒仍保留并准确报告，不重挑到有利结果。

最小规模矩阵为原输入、中间规模、长任务目标规模。两天内资源不足时，原输入和长目标两级必须完成；中间规模标为诊断。每行列 index/geometry、query、candidate/hit/output 大小和数据来源；查询数增加但命中密度不变，不得声称覆盖了密集相交或最坏情况。

### 3.1 Graph RT-2A1：优先完成

现有 com-dblp prepared C 约 0.437 秒；first execute 约 1.313 秒不等于稳定长任务。先核验已登记 SNAP 数据及 checksum，按 com-dblp → cit-Patents → soc-LiveJournal1 顺序探索 C 的一次完整整图计数，选首个可行的 1–10 秒规模，不切掉昂贵分段。输入入口见 `experiments/v4_paper_apps_pyoptix/inputs.py` 的 `load_triangle`；真实数据登记见 `scripts/goal5776_real_scale_runtime_inputs.py`。大图 oracle 必须绑定所用清洗/定向规则，不能仅抄公开总数。

两臂均计入全部确定性分段、每段所需 GAS/数据和最终 checked U64 总数。分段内存限制、Float32 精确索引边界、溢出限制先检查。没有拿到大图字节或可验证输出时，该输入保持未完成，不用合成复制图冒充真实数据。

### 3.2 Particle：扩大真实单步批量，谨慎处理完整轨迹

先使用同一真实网格中不同且有效的粒子查询扩大一个自然 batch；记录采样规则、seed、去重/有效性、网格规模和输出矩阵大小。不得简单复制 5,000 个查询数千次后称更大场景。若运行完整多步 tracking，必须执行应用真实状态更新和依赖，并校验越界、miss 与终止；没有实现这些就准确称大批量 cell-transition 阶段。

现有 A 的 canonical any-hit collector 与 C 的 native closest-hit 物理算法不同。不能删掉 canonical tie/boundary 语义换速度。若增加 native closest-hit lowering，必须有明确适用契约、可检查前提或正确 fallback，保持原有广义路径；不能把“在这组输入看不到 tie”当普遍安全证明。

### 3.3 LibRTS point/range：扩大真实索引与不同查询

先检查原空间数据及 query 文件可用规模；从更多真实对象/不同查询构造长任务，固定 point/range predicate、坐标规范化、边界、输出 count 及 overflow 规则。若必须生成查询，登记其分布和 seed 并明确 synthetic queries on real data，不称原论文原始查询。不得通过任意扩大范围让输出义务改变，也不能只重复既有少量查询。

现有查询 C 约 0.23 ms，而准备数秒。已有 Setup + run 超过一秒不足以满足本项；要提供有实质查询工作的批量，报告吞吐与绝对延迟、内存用量及命中分布。物理 AoS/SoA、flags 和 count kernel 不同的情况继续披露。

## 4. 按证据优化，先不改变算法语义

先做未进入正式样本的层次诊断：域预处理、前端/编译、module/pipeline/SBT、GAS、H2D、OptiX traversal、归约、D2H、公开返回/检查。异步阶段不得把不相加的重叠 event 时间当总墙钟分摊；附同步点和工具开销说明。没有阶段计时只可称源码候选原因。

| 路径 | 第一优先级 | 保留与验收 |
| --- | --- | --- |
| Graph | 把 immutable PTX/module/program-group/pipeline/SBT 复用与每段 GAS/输入分开，减少每段重复 executor 生命周期 | 同一通用 leaf 和正确 entry；全部分段计数、U64 overflow、逐段错误与最终结果正确；输入/几何变化不能错误复用 GAS |
| LibRTS | 先合并重复物化/拷贝与不必要同步；同 stream traversal→checked reduction→状态/结果返回；再评估布局和 build flags | 仍同步确认 native/status/result 后返回；不关验证，不丢 retry/close 所有权；每项改动有独立阶段证据 |
| Particle | 先削减 NumPy/ctypes/native 间重复 materialization、多列重复上传和诊断搬运；复用只限有效 immutable 对象 | 修改输入、close 后用、错误 thread/process、失败路径、边界/tie 的原契约不削弱；不可把旧 collector 保障静默删掉 |

优化应落在通用 shape/operation/lifecycle 层，不能在引擎中根据 app 名、特定输入 hash、期望答案或测试规模分派捷径。新增 specialized lowering 必须标出适用范围、真实实现与 TCB 成本，不能冒充一般用户源码性能。

诊断与正式结果分开。只写能验证实际优化风险的测试，复用已有回归；涉及缓存时检验失效与生命周期，涉及归约时检验零/极端/overflow，涉及 OptiX entry 时检验真实调用和输出，不能只验证字符串相同。

## 5. 计时和预注册

### 主端点

- **完整应用/阶段墙钟**：双方从同一内存中的领域输入出发，到完整可消费结果；计入必要 encoding、index/geometry、全部 rounds、结果构造与同步。读盘可共同排除；明确阶段还是完整 app。
- **Prepared 自然计算墙钟**：允许同样的静态状态和代码准备后，完成一个完整自然 batch 或整图计算。准备时间单列；不能在主结果中丢掉。没有有意义的 prepared 接口则标 N/A。
- 部署/冷启动是补充端点。两臂 AOT/precompiled 与 runtime 状态必须明确，不能混成 intrinsic language speed。

外部独立 oracle 统一放在计时后；公开实现本来必需的检查仍在计时内。若保留计时内实验 adapter digest/oracle，另列含这些工作的端点，并说明开销，不能把它默称纯语言成本。变更此测量协议是新事务，与旧数据不直接拼接。

每个正式输入/端点八个 paired blocks，四个 A-first 和四个 C-first，固定交替顺序；不同 block 使用 fresh process。prepared 先一次 untimed warmup，再默认三次完整自然计算，避免对一秒以上任务机械重复 32 次耗尽预算。其他重复数必须在正式前按耗时预算登记。每块取各臂中位数再相除，最终报告八个比值中位数和全范围；另报各臂中位时间、配对绝对差、query/second 与准备时间。不能用两个总中位数相除替代 paired estimator。

先进行双方输出 dry run，再冻结 source/input/config/环境/arm产物、worker次数、顺序、timeout/OOM规则和分析脚本，提交后开始正式 worker zero。超时阈值依 C 和既有 A 诊断成本事先设置，建议 `max(120 s, 10 × calibrated C)` 作为起点并核预算，不因观察 A 慢就事后删改。达到阈值的 A 记录 timeout 及比值下界，不能填一个准确 ratio，也不能继续超预算占卡。

只对准备用于论文的修复候选做完整正式矩阵，开发阶段使用明确非正式诊断。正式中有失败则保留整个事务，修复后新建 successor；不能只重跑失败 block 混入旧统计。

## 8. 首轮独立审查后的实施裁定（01:20 ET）

本节统一三个协作审查建议；本文件是执行指令，其他 audit 是证据和建议，不自动增加硬门槛。

- **优先小而通用的修复。** LibRTS 的 audit.open 显式传 path 导致两次 `Path.resolve`，共用 capture helper 又 resolve；loader 已有按精确 library object 绑定的 resolved path/digest registry。先诊断并利用这个已验证身份避免每次文件系统解析，外部显式 path 的严格校验保留。Particle/Graph 同样经过 capture。先验证此修复，再决定是否需要较大的 integrated-native/compact-ABI 改动。DSO digest 已按 loaded handle 缓存，不能把旧差距归于每次重 hash。
- **先行核心矩阵采用 240 workers。** 四旧单元 × old A/new A/C × 两端点 × 八块为 192；一个经 C-only 选择的真实大图 × 三臂 × 两端点 × 八块为 48。旧 prepared 维持 Particle 32/其余4；大图每 worker 三次完整 action。该批最多关闭“四旧单元修复+一个真实长图”，其他长任务和九应用覆盖继续明确列缺项，不能假称全部完成。
- **一秒是工作量标准，不制造脆弱的额外统计关。** 校准使用三个 fresh C processes，逐次报告，按三次单次自然 action 的中位数≥1秒选首个可行规模；正式全部C时间照报。偶发0.99秒不构成删样本或挑选新规模的理由，亦不把八块全部≥1秒另立为用户没要求的硬关。
- **完整计算和冷启动分开。** 新完整领域端点可让双方已有相同允许的代码/runtime readiness，计入任务所需全部领域转换、数据准备、计算与返回/close。无需为了完整性强制把 import/context 再塞入这个端点；若测冷部署另列。原 source/precompiled 不对称必须披露，不能为同形而削弱 C。预处理巨大的情况下同时看 prepared，不用共同准备掩盖差距。
- **失败留证必须改。** 新 worker 每次调用后追加并持久化记录；后续 execute/close/timeout 不丢先前样本。完整 schedule 在 worker zero 前保存，超时 bytes/str stdout/stderr 都保留，清理进程组。正式预算按实际已授权资源核定，timeout 必须覆盖整个 worker 的 load/prepare/warmup/所有calls/close；建议值不能机械套到整进程而误杀大任务。
- **节奏以本文件0–24小时交付为优先。** 协作协议中的48小时排程仅是最坏参考，不能主动把可完成的修复拖到投稿前。第一批有效结果立即提交给 lead 验证。
