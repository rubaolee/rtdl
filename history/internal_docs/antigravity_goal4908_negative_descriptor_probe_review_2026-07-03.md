### 4. Is the interpretation credible that extra Python tuple/list construction for no-xsect kept chains outweighed the saved branch logic?
**Yes.** The explanation is highly credible.
* The probe processed `5,140` fast no-xsect kept chains, containing `138,988` points (as verified under `goal4886_writer_skip_plan` in the JSON summary).
* In the proposed fast path inside [write_output_chains_streaming_numba_skip](file:///C:/Users/Lestat/Desktop/work/rtdl_v0_4_release_prep_review/history/internal_docs/goal4886_section57_public_primitives_overlay_numba_harness.py#L98-L310), the loop attempted to construct large lists of point tuples directly in Python to bypass branch checks.
* In Python, constructing and allocating `138,988` tuples and list wrapper objects introduces significant CPU and memory allocation overhead.
* This allocation cost far outweighed the small savings of skipping CPU branch checks in the loop. The results confirm that Python-layer overhead is dominated by object construction rather than basic control-flow branches.

### 7. Should the next work stop Python micro-fast-paths and either pursue a real compiled descriptor design or switch to cold/setup optimization?
**Yes.** The failure of the Goal4908 probe demonstrates that Python-layer micro-tuning (reshuffling loops, skipping branches) has reached a hard limit of diminishing returns because of Python runtime allocation limits.
* Any further writer loop optimization should avoid Python-side reconstruction and instead implement a genuinely compiled descriptor design where Numba or a C extension computes the chain descriptors, point IDs, and layout metadata directly in memory, leaving Python to perform only the final text serialization.
* Alternatively, the engineering effort should redirect to other significant bottlenecks, such as the cold setup phase (which takes ~11.6s setup time) or the point-location query step (vertex PIP map0 in map1 is `~1.1s`).
