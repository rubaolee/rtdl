## Executive Summary

The code changes and audit report for **Goal4943** have been reviewed. The audit correctly identifies the current capabilities and gaps for both the **Linear Scan Index (LSI)** / segment-pair and the **Producer Input Progress (PIP)** / directed segment point-location primitives.

Specifically:
- **LSI** Layer 1 support is complete with the addition of the generic [device_column_row_buffer_from_native_pair_columns](file:///C:/Users/Lestat/Desktop/work/rtdl_v0_4_release_prep_review/src/rtdsl/device_column_row_buffer.py#L204) adapter. This adapter extracts only the generic identity columns and preserves non-residency boundaries for full exact witness rows.
- **PIP** is correctly identified as incomplete at the Python level. Although the native C++ layers have symbols to write device points, the Python runtime does not yet expose device pointers or return carriers. Thus, PIP is properly classified as having a pointer-carrier gap (`native_symbols_present_python_pointer_carrier_missing`).

All tests run and pass successfully. The review answers below address each of the ten specific questions in the call for review.

**Yes.** The report correctly identifies that a Python-visible native device-column producer is available.

### 2. Is `device_column_row_buffer_from_native_pair_columns(...)` a generic pair-column adapter rather than a RayJoin-specific shortcut?
**Yes.** The function [device_column_row_buffer_from_native_pair_columns](file:///C:/Users/Lestat/Desktop/work/rtdl_v0_4_release_prep_review/src/rtdsl/device_column_row_buffer.py#L204-L260) acts as a generic pair-column adapter. It converts a generic two-column object (exposing `left_ids_device_ptr` and `right_ids_device_ptr`) to a standard [RtdlDeviceColumnRowBuffer](file:///C:/Users/Lestat/Desktop/work/rtdl_v0_4_release_prep_review/src/rtdsl/device_column_row_buffer.py#L36). It contains no references to `RayJoin`, polygons, or application-specific schemas. Unit tests enforce this separation by verifying that the string `"rayjoin"` is completely absent from [device_column_row_buffer.py](file:///C:/Users/Lestat/Desktop/work/rtdl_v0_4_release_prep_review/src/rtdsl/device_column_row_buffer.py).

### 3. Does the LSI adapter correctly carry only generic `left_id/right_id` columns into `RtdlDeviceColumnRowBuffer` and v2.6 neutral handoff?
**Yes.** The adapter extracts only the pair-id columns (by default named `left_id` and `right_id`) and maps them as [RtdlRawCudaColumn](file:///C:/Users/Lestat/Desktop/work/rtdl_v0_4_release_prep_review/src/rtdsl/hit_stream_handoff.py#L273) instances inside the [RtdlDeviceColumnRowBuffer](file:///C:/Users/Lestat/Desktop/work/rtdl_v0_4_release_prep_review/src/rtdsl/device_column_row_buffer.py#L36). Other fields present on `OptixNativeDevicePairColumnOutput` (such as `left_ordinals_device_ptr`, `right_ordinals_device_ptr`, and `relation_status_device_ptr`) are intentionally excluded. This guarantees that only the two generic identity columns cross the v2.6 neutral handoff boundary.

### 4. Does the packet avoid claiming that full exact LSI witness rows are device-resident?
**Yes.** The audit report strictly maintains this boundary, explicitly noting that full exact LSI witness rows are *not* device-resident. The host-resident query route (`run_pair_id_rows(...)`) continues to return a host-bound `OptixRowView` instead of device pointers. Only the candidate segment-pair IDs generated by `candidate_device_columns(...)` are device-resident.

### 5. Does the report correctly identify that PIP has native device count/write symbols but lacks a Python-visible pointer carrier?
**Yes.** The report correctly lists the native C++ symbols present in [rtdl_optix_prelude.h](file:///C:/Users/Lestat/Desktop/work/rtdl_v0_4_release_prep_review/src/native/optix/rtdl_optix_prelude.h) (e.g., `rtdl_optix_write_prepared_directed_segment_point_location_2d_device_face_ids` and its RayJoin aliases) that write point location outputs directly to device memory. It also correctly highlights that the Python runtime methods (e.g. `write_face_ids_device_points` in [optix_runtime.py](file:///C:/Users/Lestat/Desktop/work/rtdl_v0_4_release_prep_review/src/rtdsl/optix_runtime.py)) only return metadata dictionaries containing row counts, e.g. `{"row_count": ...}`, and do not expose device pointers or wrap them in [RtdlRawCudaColumn](file:///C:/Users/Lestat/Desktop/work/rtdl_v0_4_release_prep_review/src/rtdsl/hit_stream_handoff.py#L273) objects.

### 6. Is it correct to classify PIP as `native_symbols_present_python_pointer_carrier_missing` rather than complete Layer 1 producer support?
**Yes, this classification is strictly correct.** Since the Python layer has no mechanism to access the underlying device pointers or coordinate lifecycle details for downstream Numba or CuPy integration, it represents a real product gap. PIP cannot be claimed as "complete" for Layer 1.
