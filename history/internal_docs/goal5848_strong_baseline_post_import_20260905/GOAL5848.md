# Goal5848: strong-baseline and post-import performance closure

Date: 2026-09-05

Status: `IMPLEMENTED_AND_LOCALLY_AUDITED__FORMAL_GPU_EVIDENCE_0_OF_2`

Review mode at definition time: internal hostile self-review. External review
is a later manuscript-claim gate and is not implied by engineering completion.

## 1. Purpose

Close the remaining performance concern that matters to RTDL's CGO argument:
after implementation imports have completed, can a signed, precompiled RTDL
program reach its first correct result with no material disadvantage relative
to an equivalently optimized Python/OptiX implementation, while retaining
whole-protocol admission, executable identity, physical OptiX evidence and
fail-closed execution?

Goal5848 must also establish a strong steady-state lower-bound comparison. It
must not use PyOptix dependency-import latency or an avoidably host-heavy
PyOptix continuation as evidence that RTDL's abstraction is cheap.

### Acceptance at a glance

| Dimension | Mandatory gate |
| --- | --- |
| Tasks | Relation and triangle both pass |
| Strong post-import comparison | RTDL/optimized-PyOptix paired median `<=1.20x` for each task and GPU generation |
| Worst post-import block | Every RTDL/optimized-PyOptix block `<=1.35x` |
| Native lower bound | Prepared RTDL-public/Direct-OptiX paired median `<=1.20x` for each task and generation |
| Regression | Successor/predecessor RTDL paired median `<=1.05x` on the same host |
| Artifact reuse | Zero compiler invocations and cache-hit median `<=1.0 s` and `<=0.10x` cold build |
| Safety | Exact outputs, true OptiX receipts, compiler-free deploy and every registered mutation rejected |
| Generality | Complete transaction passes independently on two RTX architecture generations |
| Evidence | No discard/retry/pooling; standard-library authority recounts every byte and gate |
| Claim | Internal completion only; external review remains mandatory for manuscript wording |

## 2. Evidence that motivates the goal

Goal5847 closed its exact deployable-AOT target but exposed the next debt on
one RTX 2000 Ada GPU:

| Endpoint | RTDL | Pinned PyOptix | RTDL/PyOptix |
| --- | ---: | ---: | ---: |
| Complete process to first correct result | 1,413.776 ms | 6,163.251 ms | 0.229370x paired median |
| Post-import to first correct result | 637.846 ms | 263.349 ms | 2.504242x paired median |
| Prepared steady execution | 299.403 us | 3,496.252 us | 0.085635x pooled descriptive ratio |

The complete-process advantage is dominated by the PyOptix/CuPy import stack.
The steady advantage includes different continuation strategies: RTDL performs
generic device semantic compaction, while the pinned PyOptix arm transfers raw
events and canonicalizes them on the host. Both numbers are valid for their
frozen public contracts, but neither isolates RTDL's abstraction cost against
an equally optimized implementation.

The post-import RTDL median contains approximately:

| RTDL phase | Goal5847 median |
| --- | ---: |
| Signed deployment install | 47.240 ms |
| Provider initialization start | 4.262 ms |
| Artifact and authority load | 72.566 ms |
| Provider bind and initialization join | 269.734 ms |
| Static input deployment | 58.660 ms |
| Dynamic input deployment | 42.793 ms |
| Native prepare | 53.815 ms |
| First complete execution | 2.946 ms |

The real target is therefore the generic control plane around an already
precompiled RT operation, not the approximately 3 ms first RT execution.

## 3. Research and engineering questions

Goal5848 answers four bounded questions:

1. Which exact subphases account for RTDL's post-import disadvantage?
2. Can those costs be removed or overlapped without removing a decision-bearing
   admission, trust, physical-binding or dynamic-execution check?
3. What is RTDL's overhead against PyOptix and Direct OptiX when all arms use
   equivalent device-side continuation and return the same public output?
4. Can exact artifact reuse avoid paying the first-ever AOT build again, while
   retaining content and trust identity?

This goal does not attempt to prove that RTDL is intrinsically faster than
Python, PyOptix or native OptiX. Its target is no material abstraction penalty
for two frozen generic protocol families.

### 4.2 Weighted triangle checked-U64 scalar

## 5. Mandatory comparison arms

Every task and GPU generation must execute all applicable arms in one balanced
transaction.

### A. RTDL AOT public arm

- Ordinary public family route only.
- Signed, family-bound, precompiled `.rtdlexe` deployment.
- No private handle unwrapping and no checker-off path.
- No runtime source compilation, eager NVRTC dependency or compiler attempt.
- Exact compact public result and fresh physical execution receipt.

### B. Idiomatic pinned PyOptix arm

- Preserve the existing pinned compatible implementation as a user-facing
  reference point.
- Precompiled PTX for the formal deploy experiment.
- Its current continuation strategy must be disclosed, not silently upgraded
  after timing.

### C. Strong optimized PyOptix arm

- Independently load precompiled device programs through the PyOptix-compatible
  surface.
- Use device-side compaction/reduction equivalent to the RTDL arm.
- Return the same canonical relation bytes or checked scalar; do not transfer
  raw events merely to perform avoidable host continuation.
- No source compilation inside a measured endpoint.
- OptiX driver compilation of already frozen PTX during module creation is
  permitted and timed; CUDA/Numba/NVRTC source compilation is not.
- It may use ordinary CUDA support needed by a competent implementation, but
  every support module, kernel and launch must be frozen and disclosed.
- It must not call RTDL public or private runtime code.

### D. Direct CUDA/OptiX arm

- Native lower-bound implementation with equivalent traversal, device
  continuation and public output.
- Same geometry, query bytes, launch count and result contract.
- No validation-off RTDL component may be presented as Direct.

### E. Pre-Goal5848 RTDL regression control

- The exact accepted Goal5847 implementation, rebuilt from its bound source
  commit, is used only for same-hardware before/after regression comparison.
- Historical timings from another machine may not be divided into current
  timings.
- This arm is not pooled into PyOptix or Direct comparisons.

## 6. Baseline competence gate

Formal performance measurement is forbidden until a timer-free preflight and
internal hostile review establish all of the following:

1. All four primary arms return the exact same public output.
2. The optimized PyOptix and Direct arms use device continuation rather than
   the idiomatic relation arm's host canonicalization.
3. RTDL, optimized PyOptix and Direct perform the same required OptiX traversal
   count and equivalent public-output transfer.
4. The optimized PyOptix median steady time in a nonformal engineering run is
   no more than `1.05x` the idiomatic PyOptix median for each task. If this
   condition fails, the alleged strong baseline is not competent and must be
   repaired before formal timing.
5. Source, PTX/cubin, native binaries, package versions and every support
   kernel are hash-bound before worker zero.
6. No arm compiles device source during any registered deploy or execution
   endpoint. Driver loading/JIT of frozen PTX is recorded separately and is
   not mislabeled as source compilation.

A baseline that is unavailable, incorrect or slower because of an avoidable
harness defect is not evidence in RTDL's favor. It blocks the goal.

## 7. Required generic implementation work

The implementation must be driven by measured phase cost. The expected work
packages are the following, but an optimization enters the accepted result
only if its attribution evidence shows that it removes real work.

### 7.1 Partition the post-import endpoint

Instrument non-overlapping per-worker intervals for:

- trust-root and deployment-package discovery;
- artifact metadata decoding;
- artifact/native/PTX byte reads and hashing;
- RSA verification;
- native DSO load and symbol binding;
- CUDA context creation;
- OptiX module/program-group/pipeline/SBT creation;
- provider initialization wait not explained by the preceding subphases;
- static-input validation and allocation;
- dynamic-input validation and allocation;
- host-to-device transfer;
- GAS build or reuse;
- first complete execution and public-output validation.

For each worker, the partition plus explicitly measured timer overhead must
reconcile with the endpoint within the greater of `2 ms` or `1%`.
Instrumentation overhead must be measured and must not exceed `5%` of the
uninstrumented endpoint median.

### 7.2 Remove redundant artifact work

- Parse each immutable artifact/trust document at most once per deployment.
- Hash each immutable byte stream once and pass an immutable verified view or
  digest capability to later layers.
- Prefer safe mmap or typed immutable views to repeated Python byte copies.
- Preserve independent binding among trust root, package, artifact, executable,
  family, native provider and target.
- A cache hit is valid only when all identity inputs match exactly.

### 7.3 Complete safe overlap

- Start independent provider initialization before CPU artifact verification
  where the lifecycle permits it.
- Overlap file reads, hashing and signature verification with CUDA/OptiX
  initialization without publishing a capability early.
- The final bind must join both sides and reverify all cross-side identities.
- Initialization failure, abandoned install, concurrent bind/close, post-fork
  use and cross-family binding must remain fail closed.

### 7.4 Eliminate input materialization duplication

- Construct static and dynamic typed columns once from canonical fixture bytes.
- Avoid list/tuple/dict intermediates on the optimized deployment route.
- Reuse immutable static target state when exact identity permits it.
- Keep dynamic query identity, generation and ownership checks explicit.
- Do not introduce task-name dispatch or application predicates into the
  engine.

### 7.5 Reduce native prepare cost

- Separate reusable module/pipeline/static-GAS state from per-query state.
- Reuse prepared state only under exact device, process, family, artifact,
  native-library, static-input and ABI identity.
- Any mismatch, failed transition or use-after-close invalidates reuse.
- A persistent service or daemon is outside the fresh-process comparison and
  may not be used to make that endpoint appear faster.

### 7.6 Bound first-ever AOT work

- Decompose the current approximately 94.171 s first materialize/build/sign
  path into compiler, native build, packaging, hashing and signing phases.
- Add exact content-addressed reuse so a repeated identical request performs
  zero compiler invocations.
- Cold first-ever compilation remains a separately reported metric. It is not
  moved into an undocumented installation step and is not pooled with deploy.

## 8. Security, correctness and architecture invariants

Every accepted implementation must satisfy all of these conditions:

1. Whole-protocol admission remains enabled on the public RTDL arm.
2. RTDL deploy and execution report zero runtime-compiler attempts.
3. The AOT runtime has no eager NVRTC dependency and maps no runtime compiler.
4. Public output is unavailable until dynamic native status and the compact
   execution receipt pass validation.
5. Relation and triangle results exactly match independent oracles.
6. Every execution records the required real OptiX launches, raygen count,
   traversable identity, output digest and monotonic execution identity.
7. At least the following isolated mutations fail closed: artifact bytes,
   authority bytes, native DSO bytes, PTX bytes, trust package, cross-family
   bind, unknown deployment slot, prepared-input identity, stale process,
   wrong thread, initialization failure, bind/close race, output bytes,
   launch count and receipt digest.
8. Ordinary performance mode does not disable a decision-bearing check. Full
   forensic expansion may remain explicit and off the ordinary fast path.
9. Native symbols and runtime branches remain generic bounded-relation or
   checked-reduction behavior. No RayDB, graph, collision, paper-app predicate
   or force formula enters the engine.
10. Goal5847's evidence and adverse intermediate attempts remain immutable.

## 9. Experimental design

Exploration, optimization and formal evidence are separate stages.

### 9.1 Exploration stage

- Run phase profiling and causal A/B diagnostics.
- Optimize only measured dominant phases.
- Preserve every adverse engineering result in the engineering log.
- Exploration values cannot be pooled into formal estimates or cited as the
  final result.

### 9.2 Freeze stage

Before formal worker zero, commit and hash-bind:

- source tree and implementation commit;
- exact task inputs and expected outputs;
- all arm source and dependency revisions;
- all PTX/cubin/native binaries and build manifests;
- environment probe and supported-version decisions;
- worker/controller/authority-builder source;
- arm order, task order, block count, warmup count and sample count;
- endpoint definitions, estimators and every acceptance threshold;
- no-retry and no-discard policy.

No formal-worker timing result may be inspected before this freeze is
committed. Earlier exploration timings remain labeled nonformal and cannot be
pooled into or substituted for the formal transaction.

### 9.3 Formal schedule per GPU

- Two mandatory tasks.
- Four primary arms A through D.
- Eight balanced blocks.
- A fresh process for every task/arm/block cell.
- Latin-square or equivalently balanced arm order; task order alternates.
- At least 16 warmups and 128 retained steady samples per worker.
- Exactly 1,024 steady samples per task/arm when all eight workers pass.
- Zero discretionary sample discard.
- One separately scheduled predecessor RTDL regression control per task/block.
- Idle-GPU and environment checks occur before worker zero and are not used to
  reject an otherwise valid completed worker.

A worker crash, wrong output, missing receipt, compilation attempt, schema
error or custody failure terminates the transaction. Repair requires a new
versioned preregistration and a complete fresh transaction. Prior rows are
retained but never pooled.

### 9.4 Endpoints and estimators

Primary endpoint:

- `implementation_import_end -> first exact public result` in a fresh process.
- Includes fixture materialization, trusted deployment, provider setup, input
  deployment, native prepare, first complete execution and result validation.

Primary estimator:

- median of the eight within-block RTDL/strong-PyOptix ratios, independently
  for relation and triangle.

Secondary endpoints:

- parent pre-spawn to first exact result;
- prepared complete same-contract execution;
- RTDL public path versus Direct OptiX;
- current RTDL versus pre-Goal5848 RTDL on the same GPU;
- first-ever AOT build and exact-repeat AOT cache hit;
- all partitioned startup phases.

Ratio-of-pooled-medians may be reported descriptively but may not replace the
registered within-block estimator.

Instrumentation overhead uses a replicated pair-first rule. For each task and
each of eight preregistered blocks, 16 plain and 16 instrumented fresh processes
are retained. The block ratio is the instrumented endpoint median divided by
the plain endpoint median. The registered overhead is the median of the eight
block ratios minus one, clamped at zero, and must remain at or below 5%.
Marginal ON and OFF medians are descriptive only. This v3 estimator follows
two retained pre-formal Goal5850 failures documented in
`../goal5850_instrumentation_pairing_repair_20260905.md` and
`../goal5850_instrumentation_replication_repair_20260905.md`; no failed sample
is reused or relabeled. The v3 authority must bind every worker and process
file; both the preflight finalizer and the final transaction authority must
recompute the replicated result rather than trust the instrumentation
producer's pass bit.

## 10. Hard acceptance criteria

Goal5848 is internally complete only if every criterion below passes. A
favorable relation result cannot compensate for an adverse triangle result,
and one GPU cannot compensate for a failure on the other.

### AC1. Exactness and physical execution

- All arms match both frozen outputs in every preflight and formal worker.
- RTDL receipts prove the required true OptiX launches and exact public-output
  boundary.
- `0` registered correctness failures and `0` missing receipts.

### AC2. Strong-baseline validity

- Strong PyOptix passes the competence gate for both tasks.
- Strong PyOptix and Direct use device-resident continuation and compact public
  transport equivalent to RTDL.
- No registered endpoint performs source compilation.
- An internal hostile review finds no known avoidable baseline handicap.

### AC3. Post-import parity

On each GPU generation and each task:

- median of within-block `RTDL / strong PyOptix <= 1.20x`;
- every individual block ratio `<= 1.35x`;
- all eight blocks and all registered samples are retained.

Failing either task or either bound leaves Goal5848 open.

### AC4. Native lower-bound proximity

On each GPU generation and each task:

- median of within-block prepared-steady `RTDL public / Direct OptiX <= 1.20x`.

This gate measures the remaining public abstraction tax. An RTDL algorithmic
speedup elsewhere does not cancel a failure here.

### AC5. No prepared-path regression

On the same GPU and task, using the separately scheduled predecessor control:

- median of within-block `Goal5848 RTDL / pre-Goal5848 RTDL <= 1.05x`.

Historical absolute timings from a different machine are descriptive only.

### AC6. Deploy path remains compiler-free

- No RTDL process imports a compiler lifecycle module, maps NVRTC, exposes a
  source-compiler entry point or records a runtime compiler attempt.
- The deployed native DSO export and dependency surface exactly matches its
  frozen allowlist.

### AC7. Security does not regress

- All local lifecycle/security tests pass.
- All registered isolated mutations in Section 8 fail closed before public
  output.
- Overlap, caching and reuse do not weaken PID/thread ownership, one-shot
  initialization, trust, family, executable, input or output binding.

### AC8. Artifact reuse

- An exact repeated AOT request performs zero compiler invocations.
- Its median cache-hit duration is no more than `0.10x` the same-host cold
  first-build duration.
- Its median cache-hit duration is also no more than `1.0 s` from request to
  verified reusable artifact capability.
- Cold build and cache-hit absolute phase times are both reported.

This criterion does not claim that the remaining first cold compilation time
is acceptable; it prevents repeated identical requests from paying it again.

### AC9. Cross-generation replication

- The complete frozen experiment passes independently on two distinct NVIDIA
  RTX architecture generations supported by the implementation.
- Source, task, protocol and estimator bytes remain identical. Native and
  device artifacts may be rebuilt per architecture before worker zero, but
  each build must derive from the frozen source and be independently
  manifest-bound for that host.
- No fixed cloud vendor, driver branch or GPU model is required in advance.
- Each host is probed and recorded; unsupported environments fail explicitly.
- Raw times are not divided across machines. Only gate direction and
  independently computed within-machine ratios are compared.

### AC10. Reproducible authority

- A complete evidence archive contains every worker, stdout/stderr, task,
  binary, PTX/cubin, build receipt, environment record and preregistration.
- A standard-library-only authority builder independently verifies archive
  safety, all hashes, Git blobs, binaries, outputs, receipts, samples,
  estimators and gates.
- Hostile authority tests reject path traversal, byte substitution, coherent
  receipt resealing, sample mutation, threshold mutation and signature
  mutation.
- Fresh local recount is byte-identical to the stored authority.

### AC11. Repository quality

- Goal5848-focused tests pass.
- Relevant current-path adjacent tests pass, with any unrelated historical
  artifact failures enumerated rather than hidden.
- Lint and `git diff --check` pass.
- Final source, evidence, report and authority are committed and pushed from a
  clean branch.

### AC12. Review and claim boundary

- Strict internal hostile self-review has no unresolved P0/P1 finding inside
  the bounded goal.
- External review remains required before public/manuscript performance
  wording. Internal completion must use exactly:
  `PASS__GOAL5848_INTERNAL_TECHNICAL_COMPLETE__EXTERNAL_REVIEW_PENDING`.

## 12. Failure policy

Goal5848 is not complete if any hard criterion fails. In particular:

- a `4.36x` complete-process win cannot hide post-import failure;
- a `11.68x` idiomatic-PyOptix win cannot replace the strong baseline;
- a relation pass cannot hide a triangle failure;
- one GPU cannot establish the two-generation result;
- disabling validation cannot repair performance;
- moving work before an undocumented timer boundary cannot repair performance;
- changing the task, output, baseline or threshold after inspecting formal
  results requires a new preregistration and preserves the failed transaction;
- unavailable or broken baseline code blocks the corresponding claim rather
  than counting as a win.

If AC3 or AC4 fails, the next action is another measured generic optimization
against the dominant phase, not claim dilution. If all reasonable generic
repairs are exhausted, the final report must state the measured abstraction
cost and the exact feature that causes it; it may not declare success.

## 13. Goal-level claim on success

If every hard criterion passes, Goal5848 may support only the following
internal statement until external review:

> On two frozen app-independent RT protocol families and two RTX generations,
> signed precompiled RTDL deployment retained whole-protocol admission and
> fail-closed physical execution evidence while meeting preregistered
> post-import and prepared-execution overhead bounds against equivalently
> optimized PyOptix and Direct OptiX implementations.

It still does not prove arbitrary Callback-IR execution, arbitrary-workload
performance, universal hardware independence, usability superiority,
production signing, or an intrinsic language speedup.
